# 2026-08-30 0.5.0 typed policy redesign

## Objective
- Prepare a clean, breaking 0.5.0 API for a general-purpose CSS sanitization crate without backward-compatibility wrappers.
- Keep the upstream lightningcss AST directly available while adding sanitizer-specific typed context, capabilities, limits, errors, and reporting.

- Make the crate release-ready through tests, documentation, version/changelog, and publish dry-run.
- Do not publish, commit, push, or migrate downstream consumers in this milestone.
- Keep the repository product-neutral; no consumer-specific names, policies, or assumptions.

## Major Changes
- Files/modules:
  - `src/policy.rs`: `CssPolicy`, typed decisions and contexts, exhaustive `RuleKind`, descriptor kinds, semantic `ResourceUse`, dedicated import and dynamic-value decisions.
  - `src/sanitize.rs`: complete rule traversal, guarded opaque at-rules, dedicated import handling, pre-parser and output limits, fallible string APIs, reports.
  - `src/guard.rs`: shared typed/raw resource, variable, environment, generic-function, image-set, and token traversal.
  - `src/preset.rs`: safe `StrictPolicy` preset with explicit selectors, rules, descriptors, resource uses, local fonts, dynamic values, subrules, and dangerous import capability.
  - `src/options.rs`: `ParseLimits`, traversal budget, parser flags, strict parsing, dangerous guard opt-out.
  - `src/output.rs`: `SanitizedCss`, `SanitizeOutput`, `SanitizeReport`, typed errors, HTML style-element text serialization.
  - Tests, README, changelog, example, and benchmark were rewritten for the 0.5 API.
- API routes:
  - String: `sanitize_declaration_list[_with_options]`, `sanitize_stylesheet[_with_options]` return `Result<SanitizeOutput, SanitizeError>`.
  - AST: `sanitize_declaration_block_ast[_with_options]`, `sanitize_stylesheet_ast[_with_options]` mutate lightningcss AST and return `SanitizeReport`.
- DTO/repository/service/permission layers:
  - No application layers. Permission behavior is deny-by-default and capability-based.
  - General resources never enable `@import`; passthrough import is a separately named dangerous decision.
  - Unscoped selectors, local font probing, descriptor families, page margins, font-feature subrules, dynamic values, and resource uses require explicit capabilities.
- Worker/background jobs:
  - None.
- Migrations/entities/constants:
  - Package and lockfile root version changed from 0.4.0 to 0.5.0.
  - Default budgets: 1 MiB input, 128 delimiter nesting, 1 MiB output, 128 AST traversal depth.

## Remaining Work
- Known gaps:
  - Upstream lightningcss alpha.72 recursion issue remains open; preflight checks reduce the known risk but hostile high-availability parsing may still need process isolation.
  - The crate does not fetch/sanitize imports, resolve base URLs, validate redirects, rewrite selector scope, namespace CSS definitions, or resolve dynamic values across cascade boundaries.
  - Count-based reports do not yet contain per-item source locations or parser warning collections.
- Risks:
  - `dangerously_allow_passthrough_imports()` and `dangerously_disable_value_guard()` intentionally remove core guarantees.
  - Explicitly allowing unscoped selectors or name-defining rules can affect host CSS.
- Suggested next entry points:
  - Review the complete diff, then commit/push only when requested.
  - Publish 0.5.0 separately, then migrate downstream consumers against the published package.
  - Consider fuzzing and independent browser/parser corpus tests as a follow-up hardening milestone.

## Notes For Next Agent
- Preserve the hybrid boundary: original lightningcss AST types in hooks, crate-owned types only for sanitizer semantics and storable capability tags.
- Do not add compatibility aliases unless explicitly requested; 0.5 is intentionally a clean cutover.
- Do not silently broaden `StrictPolicy` defaults. New capabilities should remain explicit and security-named where they bypass an invariant.
- Do not claim dry-run packaging is publication.
