## Major Changes
- `sanitize.rs` owns public entry points, parsing, diagnostics, and serialization. `ast_sanitizer.rs` owns structural policy traversal and pruning. `limits.rs` owns iterative lexical limits; `value_guard.rs` owns value/resource validation. `strict_policy.rs` replaces `preset.rs`.
- The lexical guard uses cssparser 0.37, matching lightningcss alpha.72. It tracks matching delimiters iteratively, including bad strings, bad URLs, and mismatched closers. Never replace it with a handwritten quote scanner or recursive block parsing.
- Default lexical nesting is 32 (previously 128). The old scanner could be bypassed with an unescaped newline in a string; valid nested rules also exhausted a 1 MiB Windows debug stack below the old limit. Regression tests reject the known inputs and exercise accepted boundary shapes on a 1 MiB stack.
- Raw AST token lists are serialized and reparsed under input/nesting budgets before value-policy checks. This catches token combinations that print as resource functions, declarations, or `!important`. Raw bad-string, bad-URL, and raw function tokens fail closed.
- `StrictPolicy::allow_resources(uses, validator)` requires a validator per resource use. Repeated calls replace only the specified uses; cloning a policy preserves independent permission maps. Unrestricted trust is named `dangerously_allow_unrestricted_resources(uses)`.
- `allow_variables(properties)` and `allow_environment_variables(properties)` require property allowlists and do not enable properties, descriptors, or fallback resources. External cascade values remain trusted input whenever substitution is enabled.
- `SanitizeLimits` replaces `ParseLimits`, combining input/output bytes, lexical nesting, and rule depth. Use `SanitizeOptions::with_limits()` and `with_parse_mode(ParseMode::{Recover, Strict})`; old option builders and aliases were removed.
- `SanitizeReport` is non-exhaustive and exposes total parser warning count plus the first 32 warning details, with one-based positions. Policy-removal counters remain separate from parser recovery.
- `SanitizedCss` no longer implements `Display`. Choose raw `as_str()`/`into_string()`, `to_style_element_text()`, or the new quoted-attribute `to_style_attribute_value()` explicitly.
- Added `examples/restrict_resources.rs` using parsed HTTPS origins. The `url` crate is a dev dependency only; existing locked dependency versions were preserved.
- No HTTP routes, DTOs, jobs, or database migrations are involved.

## Remaining Work
- Known gaps: no outstanding implementation work for this milestone. Actual publication requires a separate user request.
- Risks: limits mitigate known parser recursion shapes, not every possible upstream exhaustion path. Increasing lexical depth requires validating the target runtime stack. Output size is checked after allocation/serialization.
- URL validators see decoded, unresolved references; callers own base URL consistency and redirect checks. External variables/functions cannot be resolved by this library. Selector isolation and definition namespacing remain caller-owned.
- AST callers must preserve lightningcss structural invariants and own their original parse and output budgets. Post-sanitization transformations need revalidation.
- Suggested next entry points: README migration guidance and `examples/restrict_resources.rs` for consumers; the dedicated input-limit, AST, resource-policy, and output test suites for further hardening.
